# Architecture

Astro keeps a strict separation between upstream Chromium and Oxy code. There are only three places Oxy-specific code lives:

1. **`patches/astro/`** — minimal, surgical patches against upstream Chromium files (hooks, includes, registrations).
2. **`src/chrome/browser/oxy/`** — the entire C++ overlay (auth, cookie observer, Alia, ad blocker, WebUI controllers).
3. **`webui/`** — the Vite + Tailwind frontends for each internal page.

Everything else is stock Chromium, checked out at the exact commit `browser.lock.json` declares by `tools/sync-sources.sh`. This makes Chromium version bumps tractable — patches rebase cleanly because they are small and the overlay is self-contained — and makes each bump a reviewable lock diff. See [Reproducibility](/reproducibility).

## Patch model

Two patch sets are applied by `tools/apply-patches.sh`, each in the order
declared by its own `series` file:

```
patches/
  ungoogled/   112 patches inherited from ungoogled-chromium (+ series)
  astro/        57 patches for Oxy integrations + branding + scheme (+ series)
```

The series file is the single source of order. It must agree with the directory
in both directions: a patch on disk that no series declares fails the run, as
does a series entry with no file behind it. Order is a reviewed decision, not a
property of `find | sort`.

Patches apply **exactly or not at all** — no fuzz, no three-way merge. Both
fallbacks yield a tree that is not the reviewed patch. Every run writes
`build/reports/patch-report.json`, on the failure path as well as on success.

Ungoogled patches handle the heavy lifting of removing Google services (sync, hangouts, mDNS, remoting, reporting, field trials, safe browsing pings, hard-coded API keys). Astro patches add what Oxy needs on top.

    ├── BUILD.gn

Naming is consistent: `oxy_*` for ecosystem-wide services (auth, Alia, cookies) and `astro_*` for browser-specific UI (WebUI controllers, ad blocker integration).

### How the overlay reaches the Chromium tree

`tools/sync-overlay.sh` copies it, and only to destinations declared in
`tools/overlay.allowlist`. Anything else is refused before a byte is written.

The whole file, as it stands — two entries, and no `overwrite` among them:

```
dir       chrome/browser/oxy                          # Astro owns it entirely
file      chrome/app/vector_icons/alia_spark.icon     # new file, Chromium-owned dir
```

The script never deletes, verifies the destination is a real Chromium checkout
first, refuses to clobber an upstream-tracked file that is not declared as an
`overwrite`, and records everything it wrote in
`build/reports/overlay-manifest.json`.

<Warning>
**The overlay is copied *after* patches are applied, so an `overwrite` of a
file a patch also modifies silently reverts that patch.** That is not a
hypothetical: a whole-file copy of
`chrome/browser/ui/webui/chrome_web_ui_configs.cc` once reverted four patches,
including `054-adblock-webui-register.patch`, so `AstroAdBlockUIConfig` was
never registered in the resulting build. It is [issue
#7](https://github.com/OxyHQ/Astro/issues/7).

The copy is gone — deleted in `c9c4383` along with the settings page that was
its only reason to exist — and with it the `overwrite` entry, which was the
only one the allowlist has ever carried. Registration is a patch again.

The warning stays because the shape is what is dangerous, not that one file:
any *new* collision of this kind fails the sync outright, and it should stay
that way. Prefer a numbered patch over an `overwrite` every time.
</Warning>

## There is no Mojo IPC pipeline

This section used to describe one, in detail: an `astro_settings.mojom` with
three interfaces, an `astro_settings_handler.cc` with two pref-mapping arrays,
a `PrefChangeRegistrar` pushing live updates to the page, and a three-step
recipe for adding a setting. None of it existed. **No `.mojom` has ever been
committed to this repository** — `git log --all --diff-filter=A -- '*.mojom'`
returns nothing at any revision — and the settings page those interfaces were
supposed to serve was deleted in `c9c4383`. What that commit actually removed
was a generic `chrome.send` handler carrying six messages and thirty-four
prefs.

Documentation that invents a file is worse than documentation that omits one:
it sends the reader looking for something to edit, and it survives every
review that only reads code.

What is true today: `astro://settings` is served by upstream Chromium's own
`settings::SettingsUIConfig`, and the Astro overlay consumes Chromium's mojom
types (`network::mojom` and friends) without defining any of its own.

The direction — one Vite + Tailwind + Bloom application behind every
`astro://` surface, with narrow typed Mojo per domain rather than a generic
`SetPref(string, value)` — is issues #15 (as amended 2026-08-08), #14, #22,
#17 and #24. It will be documented here when it exists, and not before.

## WebUI controllers

Three internal pages have a controller in `src/chrome/browser/oxy/webui/` —
NTP, Alia and What's New — plus the ad blocker's under `adblock/webui/`. All
inherit `content::WebUIController` directly; none uses Mojo.

```cpp
class AstroNtpUI : public content::WebUIController {
 public:
  explicit AstroNtpUI(content::WebUI* web_ui) : WebUIController(web_ui) {
    auto* source = content::WebUIDataSource::CreateAndAdd(
        web_ui->GetWebContents()->GetBrowserContext(), kAstroNtpHost);
    // Serves the Vite-built dist/ by reading it off disk at request time.
    // See the warning below.
  }
};

class AstroNtpUIConfig : public content::DefaultWebUIConfig<AstroNtpUI> {
 public:
  AstroNtpUIConfig()
      : DefaultWebUIConfig(content::kChromeUIScheme, kAstroNtpHost) {}
};
```

<Warning>
These pages read their assets from a directory beside the executable at
runtime (`base::DIR_EXE` + `resources/astro-<page>/`) rather than from a
`.pak`. They therefore carry none of Chromium's resource-bundling guarantees
and render blank, with no error, if the directory was not staged. Three things
have to agree — the path the controller reads, the path `tools/build.sh`
stages to, and the page's presence in `REQUIRED_WEBUI_PAGES` — and nothing
checks that they do. Removing `DIR_EXE` in favour of a real `.pak` is #14.
</Warning>

`UIConfig` registration happens in the patched `chrome_web_ui_configs.cc`, one
numbered patch per page: `054-adblock-webui-register`, `055-ntp-webui-register`,
`058-alia-webui-register`. What's New is deliberately absent — its host string
is byte-identical to upstream's, and `WebUIConfigMap::AddWebUIConfigImpl`
CHECKs on a duplicate origin, so registering beside upstream crashes the
browser at startup. Taking a host upstream already owns means SWAPPING its
registration line, never adding one.

Registration alone is not enough: a `BUILD.gn` under `chrome/browser/oxy/`
that nothing depends on compiles to nothing, silently. The edge that makes the
overlay reachable is `057-oxy-webui-build-edge.patch`, into
`//chrome/browser/ui/webui:configs`.

## Rust ad blocker

The adblock engine is a Rust crate vendored into `src/chrome/browser/oxy/adblock/rs/`. It exposes a `cxx::bridge` FFI surface that the C++ wrapper (`AstroAdBlockEngine`) calls into.

### Components

| Component | Role |
|-----------|------|
| `AstroAdBlockService` (KeyedService) | Owns the engine and filter list updater; one per profile |
| `AstroAdBlockEngine` | C++ wrapper around the Rust engine; sequence-checked, not thread-safe |
| `AstroAdBlockFilterListCatalog` | Curated list of filter lists (EasyList, EasyPrivacy, etc.) |
| `AstroAdBlockFilterListUpdater` | Background fetch + cache invalidation |
| `AstroAdBlockUrlLoaderThrottle` | Hooks into `URLLoaderFactory` to intercept and block network requests |
| `AstroAdBlockTabHelper` | Per-tab state (blocked count, allowlist) |
| `AstroAdBlockToolbarButton` + `BubbleView` | Shield icon in the toolbar + per-site controls bubble |
| `AdblockDomainResolver` | Two-level domain matching (used by the Rust engine) |
| `AstroAdBlockResourceType` | Maps Chromium `ResourceType` to ABP `resource_type` strings |

### Lifecycle

1. **Service init**: `AstroAdBlockService` constructs the engine on a background sequence. If a serialized engine exists at `<profile>/AstroAdBlock/engine.dat`, load it (fast path, ~10ms). Otherwise, fetch all filter lists in the catalog, build the engine, and serialize.
2. **Filter list updates**: `FilterListUpdater` re-fetches lists per their `update_interval`. On successful fetch, the engine is rebuilt and re-serialized.
3. **Request matching**: `URLLoaderFactory` calls `AstroAdBlockUrlLoaderThrottle::WillStartRequest`. The throttle calls `Engine::Match(url, resource_type, source_domain)` synchronously (the Rust matcher is fast enough to run on the IO thread for the hot path).
4. **Per-tab state**: `AstroAdBlockTabHelper` increments the blocked count for the active `WebContents`; the toolbar button reads it on observer notification.
5. **Allowlist**: per-domain allowlist lives in profile prefs (`oxy.adblock.allowlist.<host>`). The throttle checks this before consulting the engine.

The Rust engine itself is `brave/adblock-rust` (or a compatible fork) — re-vendor with `tools/vendor-adblock-rust.sh` when bumping the upstream version. The C++ wrapper exists to keep the FFI surface minimal and to enforce sequence safety, not to add policy.

## Authentication flow

See [Oxy integration](./oxy-integration) for the full sign-in flow, cookie observer, and token refresh. In short:

1. User clicks "Sign in" in the profile menu → opens `https://auth.oxy.so/login` in a new tab.
2. User signs in. Auth server sets the `fedcm_session` cookie on `*.oxy.so`.
3. `OxyCookieSigninObserver` (running in the browser process) is notified by the network service's `CookieChangeListener` and fetches `GET /session/user/:sessionId` + `GET /session/token/:sessionId` to obtain the user profile and tokens.
4. Tokens are stored in `OxyAuthService` (in-memory + OSCrypt-encrypted in prefs).
5. The profile menu observer fires `OnOxyAuthStateChanged(true)` and updates the UI.

The redirect-based flow with `astro://auth/callback` (handled by `OxyAuthCallbackHandler` + `OxyAuthNavigationThrottle`) is a backup path for environments where the cookie observer cannot run (e.g. embedded webviews).

## Update server

`services/update-server/` is a small Bun + Hono service that responds to the Omaha-like update check Astro makes on startup. It serves signed manifests from `releases/`. CI publishes a new release by:

1. Running `tools/package-release.sh` which builds all platforms and writes artifacts to `releases/<version>/`.
2. Generating a signed manifest (Ed25519) for each platform.
3. Uploading the artifacts and manifest to the update server's CDN.

Astro embeds the update server's public key in the binary so it can verify the manifest signature before applying.
