# Architecture

Astro keeps a strict separation between upstream Chromium and Oxy code. There are only three places Oxy-specific code lives:

1. **`patches/astro/`** — minimal, surgical patches against upstream Chromium files (hooks, includes, registrations).
2. **`src/chrome/browser/oxy/`** — the entire C++ overlay (auth, cookie observer, Alia, ad blocker, WebUI controllers).
3. **`webui/`** — the Vite + Tailwind frontends for each internal page.

Everything else is stock Chromium, checked out at the exact commit `browser.lock.json` declares by `tools/sync-sources.sh`. This makes Chromium version bumps tractable — patches rebase cleanly because they are small and the overlay is self-contained — and makes each bump a reviewable lock diff. See [Reproducibility](/reproducibility).

## Patch model

Two patch sets are applied by `tools/apply-patches.sh`, each in the order
declared by its own `series` file:

```
patches/
  ungoogled/   112 patches inherited from ungoogled-chromium (+ series)
  astro/        60 patches for Oxy integrations + branding + scheme (+ series)
```

The series file is the single source of order. It must agree with the directory
in both directions: a patch on disk that no series declares fails the run, as
does a series entry with no file behind it. Order is a reviewed decision, not a
property of `find | sort`.

Patches apply **exactly or not at all** — no fuzz, no three-way merge. Both
fallbacks yield a tree that is not the reviewed patch. Every run writes
`build/reports/patch-report.json`, on the failure path as well as on success.

Ungoogled patches handle the heavy lifting of removing Google services (sync, hangouts, mDNS, remoting, reporting, field trials, safe browsing pings, hard-coded API keys). Astro patches add what Oxy needs on top.

Every patch is named after what it does. Inspection is encouraged before any version bump — most patches are a handful of lines.

**Four numbers in the Astro range are unused, deliberately.** 007 and 035 were
removed as empty files, 012 was retired by 060, and 068 was never written — two
agents were landing patches at once and 069 was taken to avoid a collision. A
gap in the numbering is therefore not a missing patch, and the series file is
the only authority for what exists.

Whether the whole series still applies is a measurement and never an
assumption; the replay that establishes it is in
[Pipeline guards](/pipeline-guards).

### WebUI frontends

```
webui/
├── app/           # WHERE NEW WORK GOES. One Vite + Tailwind v4 + Bloom
│                  #   application serving every astro:// surface, one entry
│                  #   per WebUI host (each host is a separate origin, so the
│                  #   entry is chosen from location.hostname). Built by a GN
│                  #   action into astro_webui_resources.pak and served to
│                  #   astro://settings today; manifest.json is committed and
│                  #   is the authority for what it emits.
├── alia/          # Alia AI Panel
└── whats-new/     # What's New Page
```

The two legacy pages keep their current from-disk serving until the app absorbs
them; do not start a third one beside them. (That listing is `AGENTS.md`'s,
moved verbatim; the measurement that contradicts it is recorded in
[Known defects](/known-defects).) `webui/ntp` is GONE, not moved — see
[WebUI pages](/webui) for what replaced it.

Naming is consistent: `oxy_*` for ecosystem-wide services (auth, Alia, cookies) and `astro_*` for browser-specific UI (WebUI controllers, ad blocker integration).

### How the overlay reaches the Chromium tree

`tools/sync-overlay.sh` copies it, and only to destinations declared in
`tools/overlay.allowlist`. Anything else is refused before a byte is written.

The whole file, as it stands — two entries, and no `overwrite` among them:

```
dir       chrome/browser/oxy                          # Astro owns it entirely
file      chrome/app/vector_icons/alia_spark.icon     # new file, Chromium-owned dir
```

The script never deletes, verifies the destination is a real Chromium checkout
first, refuses to clobber an upstream-tracked file that is not declared as an
`overwrite`, and records everything it wrote in
`build/reports/overlay-manifest.json`.

<Warning>
**The overlay is copied *after* patches are applied, so an `overwrite` of a
file a patch also modifies silently reverts that patch.** That is not a
hypothetical: a whole-file copy of
`chrome/browser/ui/webui/chrome_web_ui_configs.cc` once reverted four patches,
including `054-adblock-webui-register.patch`, so `AstroAdBlockUIConfig` was
never registered in the resulting build. It is [issue
#7](https://github.com/OxyHQ/Astro/issues/7).

The copy is gone — deleted in `c9c4383` along with the settings page that was
its only reason to exist — and with it the `overwrite` entry, which was the
only one the allowlist has ever carried. Registration is a patch again.

The warning stays because the shape is what is dangerous, not that one file:
any *new* collision of this kind fails the sync outright, and it should stay
that way. Prefer a numbered patch over an `overwrite` every time.
</Warning>

## Mojo, and the pipeline that used to be fiction here

Read the history first, because it is the reason this section is written the
way it is. It once described an `astro_settings.mojom` with three interfaces,
an `astro_settings_handler.cc` with two pref-mapping arrays, and a three-step
recipe for adding a setting. **None of it existed.** No `.mojom` was committed
to this repository at any revision before 2026-08-09. Documentation that
invents a file is worse than documentation that omits one: it sends the reader
looking for something to edit, and it survives every review that only reads
code.

What exists now is smaller than that fiction, and deliberately so. Two mojoms,
in `src/chrome/browser/oxy/webui/`, built by a real `mojom("mojo_bindings")`
target:

| Interface | Direction | Bound by |
|---|---|---|
| `astro.mojom.ThemeProvider` | read — `GetTheme()`, `AddObserver` | every Astro page |
| `astro.settings.mojom.PageHandler` | write — `SetThemeMode`, `SetColorPreset` | the settings controller only |

They are registered separately in the WebUI frame binder map
(`063-astro-webui-mojo-binders.patch`), and that separation is the point: one
read-write interface would let any page that wants to READ the theme CHANGE
it. There is no `SetPref(string, value)` and there will not be — a generic
setter makes every pref in the profile writable by anything that reaches the
interface, turns the pref path into a string the compiler cannot check, and
leaves the browser nowhere to validate. Chromium's own prefs reach settings
through `chrome.settingsPrivate`, which is the only transport that carries a
pref's policy state (`controlledBy`, `enforcement`, `userSelectableValues`).

Everything else Astro plans behind an `astro://` surface — identity, sync,
updates, the new tab data plane — follows the same shape: narrow, named, one
mojom per domain. Those are issues #22, #17 and #24, and they will be
documented here when they exist, and not before.

## WebUI controllers

Five internal pages have a controller in `src/chrome/browser/oxy/webui/` —
NTP, Settings, Alia, What's New and the ad blocker. All five are built on the
shared base in `astro_webui_page.{h,cc}`, which owns the data source, the
per-host CSP table and the resource map every page is served from.

The ad blocker's was the last exception, and its move is the reason they are
all in one directory: it lived under `adblock/webui/` and served a string of
inline HTML, and `//chrome/browser/oxy:webui_controllers` already depends on
`//chrome/browser/oxy/adblock` — the new tab page reads the blocked count — so
a page controller in the adblock target reaching for `astro_webui_page.h`
would have been a GN dependency cycle.

A page is a `WebUIPage` value and a controller that passes it up. The value is
the whole of what distinguishes one surface from another:

```cpp
const WebUIPage& AliaPage() {
  static const WebUIPage kPage{
      .host = kAstroAliaHost,
      // The same multi-entry bundle every Astro surface serves; the document
      // picks its entry from the host it was served under.
      .resources = kAstroWebuiResources,
      .default_resource = IDR_ASTRO_WEBUI_INDEX_HTML,
      .csp = {.style_src = "style-src 'self' 'unsafe-inline';",
              .img_src = "img-src 'self' data:;",
              .font_src = "font-src data:;",
              .connect_src = "connect-src 'none';"},
  };
  return kPage;
}

class AstroAliaUIConfig : public content::DefaultWebUIConfig<AstroAliaUI> {
 public:
  AstroAliaUIConfig()
      : DefaultWebUIConfig(content::kChromeUIScheme, kAstroAliaHost) {}
};
```

A null CSP field leaves Chromium's default in place, which is not the same as
leaving it open: trusted WebUI already ships `script-src chrome://resources
'self'` with Trusted Types enforced, and has no default at all for
style/img/font/connect. The fields are not symmetric and a page has to say what
it needs.

<Note>
No page reads its assets from disk any more. Every `astro://` surface is an
entry of `webui/app`, compiled into `astro_webui_resources.pak` by
`//chrome/browser/oxy/webui:resources` and repacked into the browser's own
`resources.pak` by `067-astro-webui-pak-repack.patch`, so a resource a
controller names and GRIT did not compile is a link error during the build.

What this replaced needed three things to agree — the path the controller
read, the path `tools/build.sh` staged to, and the page's presence in a
`REQUIRED_WEBUI_PAGES` array — with nothing checking that they did, and the
failure was a blank page with no error. One disk-reading path survives,
`astro_webui_dev_source.cc`, and it is not compiled at all unless the
`astro_webui_dev_tools` GN argument is on; that it is off in every committed
configuration is checked by
`tools/tests/cases/webui-assets-come-from-the-pak.sh`.
</Note>

`UIConfig` registration happens in the patched `chrome_web_ui_configs.cc`, one
numbered patch per page: `054-adblock-webui-register`, `055-ntp-webui-register`,
`058-alia-webui-register` for hosts Astro invents, and
`060-settings-webui-takeover` and `071-whats-new-webui-takeover` for two
upstream already owns.

That last one is a different operation and the difference is not cosmetic.
`WebUIConfigMap::AddWebUIConfigImpl` CHECKs on a duplicate origin, so a second
config for an upstream host crashes the browser at startup — taking such a
host means SWAPPING upstream's registration line, never adding one. Doing it
under upstream's own host is also what inherits the eight extension APIs
granted by host pattern in the two `_api_features.json` files,
`settingsPrivate` among them; a page served anywhere else gets none of them,
and gets them silently. What's New is still absent for exactly the reason
settings used to be, and awaits the same swap.

Registration alone is not enough: a `BUILD.gn` under `chrome/browser/oxy/`
that nothing depends on compiles to nothing, silently. The edge that makes the
overlay reachable is `057-oxy-webui-build-edge.patch`, into
`//chrome/browser/ui/webui:configs`.

## Rust ad blocker

The adblock engine is a Rust crate vendored into `src/chrome/browser/oxy/adblock/rs/`. It exposes a `cxx::bridge` FFI surface that the C++ wrapper (`AstroAdBlockEngine`) calls into.

### Components

| Component | Role |
|-----------|------|
| `AstroAdBlockService` (KeyedService) | Owns the engine and filter list updater; one per profile |
| `AstroAdBlockEngine` | C++ wrapper around the Rust engine; sequence-checked, not thread-safe |
| `AstroAdBlockFilterListCatalog` | Curated list of filter lists (EasyList, EasyPrivacy, etc.) |
| `AstroAdBlockFilterListUpdater` | Background fetch + cache invalidation |
| `AstroAdBlockUrlLoaderThrottle` | Hooks into `URLLoaderFactory` to intercept and block network requests |
| `AstroAdBlockTabHelper` | Per-tab state (blocked count, allowlist) |
| `AstroAdBlockToolbarButton` + `BubbleView` | Shield icon in the toolbar + per-site controls bubble |
| `AdblockDomainResolver` | Two-level domain matching (used by the Rust engine) |
| `AstroAdBlockResourceType` | Maps Chromium `ResourceType` to ABP `resource_type` strings |

### Lifecycle

1. **Service init**: `AstroAdBlockService` constructs the engine on a background sequence. If a serialized engine exists at `<profile>/AstroAdBlock/engine.dat`, load it (fast path, ~10ms). Otherwise, fetch all filter lists in the catalog, build the engine, and serialize.
2. **Filter list updates**: `FilterListUpdater` re-fetches lists per their `update_interval`. On successful fetch, the engine is rebuilt and re-serialized.
3. **Request matching**: `URLLoaderFactory` calls `AstroAdBlockUrlLoaderThrottle::WillStartRequest`. The throttle calls `Engine::Match(url, resource_type, source_domain)` synchronously (the Rust matcher is fast enough to run on the IO thread for the hot path).
4. **Per-tab state**: `AstroAdBlockTabHelper` increments the blocked count for the active `WebContents`; the toolbar button reads it on observer notification.
5. **Allowlist**: per-domain allowlist lives in profile prefs (`oxy.adblock.allowlist.<host>`). The throttle checks this before consulting the engine.

The Rust engine itself is `brave/adblock-rust` (or a compatible fork) — re-vendor with `tools/vendor-adblock-rust.sh` when bumping the upstream version. The C++ wrapper exists to keep the FFI surface minimal and to enforce sequence safety, not to add policy.

Everything about `gnrt` that this engine forced the project to learn — crate
groups and where an override has to be declared, why `gnrt` writes a value only
where the key is absent, and the fact that a vendored crate CAN be edited
durably through `third_party/rust/chromium_crates_io/patches/` — is in
[Known defects](/known-defects), beside the defects that produced it.

## Authentication flow

See [Oxy integration](./oxy-integration) for the full sign-in flow, cookie observer, and token refresh. In short:

1. User clicks "Sign in" in the profile menu → opens `https://auth.oxy.so/login` in a new tab.
2. User signs in. Auth server sets the `fedcm_session` cookie on `*.oxy.so`.
3. `OxyCookieSigninObserver` (running in the browser process) is notified by the network service's `CookieChangeListener` and fetches `GET /session/user/:sessionId` + `GET /session/token/:sessionId` to obtain the user profile and tokens.
4. Tokens are stored in `OxyAuthService` (in-memory + OSCrypt-encrypted in prefs).
5. The profile menu observer fires `OnOxyAuthStateChanged(true)` and updates the UI.

The redirect-based flow with `astro://auth/callback` (handled by `OxyAuthCallbackHandler` + `OxyAuthNavigationThrottle`) is a backup path for environments where the cookie observer cannot run (e.g. embedded webviews).

## Update server

`services/update-server/` is a small Bun + Hono service that responds to the Omaha-like update check Astro makes on startup. It serves signed manifests from `releases/`. CI publishes a new release by:

1. Running `tools/package-release.sh` which builds all platforms and writes artifacts to `releases/<version>/`.
2. Generating a signed manifest (Ed25519) for each platform.
3. Uploading the artifacts and manifest to the update server's CDN.

Astro embeds the update server's public key in the binary so it can verify the manifest signature before applying.
